# Phase 4A — synthetic payment receipt upload and staff review demonstration

Base: Phase 3D.2 commit `af6ce955a0cf483c1b2acecadc6a9239d5a62f90` (branch
`phase-3d2-booking-ux`, on Phase 3D.1 `0172b32` and approved owner-demo `6146af8`).
Branch: `phase-4a-receipt-demo`. Local demonstration milestone only; publication, merge
and deployment need separate approval. The Phase 3B.3 H2 finding remains an unresolved,
separate backend blocker; no worker, migration, RPC, Storage policy or API is on this branch.

## Owner payment model (what this phase demonstrates, not implements)

Customers pay in the external GCash or banking app, then submit a receipt image. Staff
independently check the club's real GCash or bank account records. Only after a matching
incoming transaction is found may an authorized staff member record a verified payment.
A submitted image, a displayed reference or a successful upload is **never** proof of funds.
No gateway, GCash/bank API, webhook, OCR, automated approval or settlement exists or is planned
by this phase.

## Customer journey — `/booking/payment-demo`

Reached from the Phase 3D.2 confirmation and private-status previews with the same
nonsensitive sample-link parameters plus an optional whitelisted `scenario` (`held` default,
`expired`). Anything else renders the safe "Payment demo unavailable" state.

1. **Instructions**: demo reference, court and session (Asia/Manila), frozen sample total,
   method choice (GCash / Bank transfer) with steps for the external app, the recipient block
   labelled `DEMO ONLY — NO REAL TRANSFER` (no account number, mobile number, QR code or
   credential anywhere), and the disclosure that no payment is collected.
2. **Receipt image selection**: a native file input (`accept` PNG/JPEG/WebP). The file is
   checked **entirely in browser memory**: empty selection → declared type/extension → size
   limit (`paymentDemo.image.maxBytes`, 4 MB, in `lib/demo/payment.js`) → leading-byte
   signature (filename and declared MIME type are not trusted) → decode through an `<img>`.
   Failures render one `role="alert"` message, set `aria-invalid`/`aria-describedby` and
   return focus to the input. Success shows a preview (object URL), filename, type, size and
   pixel dimensions, plus Replace and Remove controls. Object URLs are revoked on remove,
   replace and unmount.
3. **Demo submission**: "Submit demo receipt" with nothing selected produces the empty
   error; with an image it shows `Receipt submitted — awaiting staff verification (DEMO)` and
   `No payment has been verified. No real receipt was uploaded.`, moves focus to the section
   heading, and announces politely. The state lives in React memory only; a reload shows
   "Awaiting evidence" again. Booking status, hold deadline and totals never change.
4. **Outcome previews**: a labelled select shows what the customer would see for rejected,
   verified (always "fictional scenario") and expired outcomes without changing the demo state.
   The `scenario=expired` link disables submission entirely: evidence cannot revive a hold.

## Staff journey — `/staff/payments-demo`

Linked from the staff sidebar (route-aware `aria-current`). A synthetic queue of five claims
covers awaiting evidence, pending review, needs resubmission, verified (fictional) and expired,
with fictional names (`Sample Customer A–E`), sample references, claimed method/amount,
`SAMPLE-…` transaction references, Manila submission times, sample images and status pills.
Filtering by state; a detail panel with the image, agreed total vs claimed amount,
"Verified money received" (₱0 unless the fictional verified scenario) and the staff warning
that a screenshot alone is never sufficient. "Simulate: reject / verified (fictional) /
Reset" change local React state only; metrics recompute from `verifiedRevenueCentavos`, so
pending and rejected claims always contribute ₱0.

## Synthetic payment states (`lib/demo/payment.js`)

`awaiting_evidence`, `pending_review`, `needs_resubmission`, `verified`, `expired`. Only
`verified` carries `verifiedRevenue: true`, and its label always says "fictional scenario".
Booking status (`demoReceipt` from Phase 3D.1), the customer claim, the review outcome and
verified money received are separate values; the frozen receipt total is reused unchanged.

## Privacy and security boundaries (verified by tests and scans)

No request other than GET/HEAD; no `/api`, Supabase, Storage, GCash or bank calls; no cookies,
localStorage, sessionStorage, IndexedDB or CacheStorage; no image bytes, names or contact data
in URLs; no `process.env` in browser code; `/booking/*` keeps `no-store`/`no-referrer`.
Sample receipt images (`public/images/receipts/`, generated by
`scripts/generate-sample-receipts.mjs`) carry a conspicuous `SAMPLE / NOT A REAL PAYMENT`
mark, fictional values only and no metadata. `vercel.json` disables Git deployments for
`phase-3d1-booking-interface`, `phase-3d2-booking-ux` and `phase-4a-receipt-demo`; the
remote Vercel project's handling of these flags is not verified from this environment.

## Not decided by this phase (owner decisions still open)

Real recipient details and how they are shown; payment deadline relative to booking start;
minimum payment opportunity; partial/over-payment handling; rejection and resubmission
deadlines; review SLA and shift coverage; evidence retention period; notification channel;
refund and cancellation terms; whether a transaction reference is mandatory. None of these
are implied by the demo copy, which labels them as pending owner approval.
